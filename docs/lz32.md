# LZ32 — ISA v1 Design Draft

## Status

Step 8 specification only. [The shared ISA](isa.md) is authoritative for encoding,
operations, flags, traps, privilege, and the Steps 9–10 API contract. LZ32 is a
configuration of that architecture, not a separate CPU. No LZ32 implementation,
ABI tooling, or executable support is introduced by these documents.

## Configuration

| Property | LZ32 value |
| --- | --- |
| WordWidth | W32 |
| General registers | 16 writable ordinary r0–r15, 32 bits each |
| PC / SP | Separate 32-bit registers |
| Status | Separate 32-bit value; NZCV/IE/U in bits 0..5, bits 31:6 zero |
| Pointer / virtual / physical / instruction address width | 32 bits |
| Address range | 0x00000000 through 0xffffffff |
| Word bytes / stack alignment | 4 / 4 bytes |
| Instruction length / alignment | 8 / 4 bytes |
| Data sizes / natural alignments | 1, 2, 4 bytes |
| Endianness | Little endian for data and instruction encodings |
| FeatureSet raw bits | Exactly 0x00000001 (BaseInteger) |

The address range is an architectural bound, not a requirement for 4 GiB of RAM.
An eight-byte instruction fetch is supported despite the absence of eight-byte
data operations. MEM size selector 3 (eight-byte data) raises InvalidWidth;
selectors 4..15 are invalid encodings. Four-byte loads, stores, pointers, and
return addresses are full-word values. LDZ and LDS of four bytes return identical
32-bit bit patterns. No arithmetic result retains bits above bit 31 in a host
u64 container.

## Execution and width examples

- LI sign-extends its signed 32-bit immediate to 32 bits: LI -1 yields
  `0xffffffff`. Encodings are the same eight bytes used in LZ64.
- A one-byte LDS of `0x80` yields `0xffffff80`; LDZ yields `0x00000080`.
  Sign extension uses source bit 7, not bit 31 or a host-container sign bit.
- ADD `0xffffffff, 1` wraps to zero with Z=1, C=1, N=V=0.
  SUB `0, 1` yields `0xffffffff` with N=1, C=1, Z=V=0 (C is borrow).
- Signed range is -2,147,483,648 through 2,147,483,647. Signed DIVS and REMS
  with MIN/-1 trap; division or remainder by zero also traps without results.
- Shift counts are modulo 32; count 32 is zero and 33 is one. Even count zero
  recomputes N/Z and clears C/V. SAR repeats bit 31; SHR fills with zero.
- MEM base `0xffffffff` plus 1 faults rather than becoming address zero.
  An aligned four-byte access at `0xfffffffc` fits through `0xffffffff`;
  range checks use the inclusive last byte, not an unrepresentable end pointer.
- PC=`0xfffffff8` can fetch eight bytes, but checked PC+8 overflows, so even
  HALT/JMP/RET there fault before effects. PC alignment is four, not eight.
- A taken PC-relative branch/call uses checked `PC + 8 + signed_i32(I)*4`.
  The mathematical displacement may exceed 32 bits; calculate it before checking
  the final 32-bit address. Untaken BR does not validate its hypothetical target.

Explicit address masking is only a bit operation. It must never substitute for
architectural address validation. Existing u64-backed address constructors
remain legal for the full u64 range; a boundary value above `0xffffffff` is
rejected by LZ32-aware validation, not silently truncated.

## Stack and provisional procedure ABI

SP is four-byte aligned and the stack grows down. CALL/CALLR atomically write the
four-byte little-endian nextPC to `[oldSP-4]`, set SP=oldSP-4, and select the
checked target. RET reads the four-byte return PC at SP, validates the target
and SP+4, then commits both. Faults do not partially modify registers or memory.
Stack return-address accesses require RAM, not MMIO or ROM. An empty initial SP
must itself be representable: `0x1_0000_0000` is not a valid top-of-stack sentinel.

The shared provisional convention uses r0–r3 for four word-sized arguments,
r0 for a one-word return, r0–r7 and NZCV caller-saved, and r8–r15 callee-saved.
Additional argument slots are four bytes. At callee entry `[SP]` contains the
return PC, `[SP+4]` argument 5, and `[SP+8]` argument 6. Callee restores its entry
SP before RET; caller reclaims additional arguments. No red zone, shadow area,
mandatory frame pointer, or implicit register saves are defined.

Narrow scalar arguments/results are extended to 32 bits according to signedness.
Pointers and return addresses are four bytes. A 64-bit scalar requires future
multiword ABI rules; v1 does not define them. This does not define C `long`,
aggregate layout, variadics, or any OS syscall number/register convention.

## Privilege and LZ64 interoperability

Supervisor/User, status layout, centralized precise traps, and interrupt behavior
are shared unchanged with LZ64. Trap entry snapshots the exact pre-entry state,
uses controller-owned resume fields rather than pushing onto the User stack,
and does not silently advance the saved original PC. SYSCALL/TRAP resume PC is
nextPC; fault resume PC is the faulting PC. RFE restores validated PC/SP/status,
not the immutable general-register snapshot, so handlers can return values.

LZ64 changes word, pointer, address, and stack-slot widths to eight bytes and
adds eight-byte data access. It does not change register count, opcode encoding,
instruction length/alignment, branch scaling, feature bits, or privilege levels.
There are no mixed-mode calls or automatic binary/ABI compatibility. Any future
cross-mode conversion must explicitly validate pointer range and data layout.

## Step 9–10 acceptance inputs

ArchitectureConfig must report W32, 32-bit words/pointers/addresses, 16 registers,
eight-byte instructions aligned to four, four-byte stack alignment, and exactly
[1, 2, 4] supported data sizes. FeatureSet accepts only BaseInteger bit 0 alone.
Step 10 tests should cover low-32-bit truncation from u64, source-width extension,
32-bit carry/borrow/signed overflow, modulo-32 shifts including zero, division
faults, checked negative/positive address deltas, and the PC/access-end boundary
examples above. These are required future tests, not tests implemented in Step 8.
