# One machine, three front ends

Step 83 asks that assembly, C and Lazen converge:

```text
Assembly ──┐
           │
C ─────────┼──→ Lazalith Object
           │
Lazen ─────┘
```

then

```text
Object
 ↓
Linker
 ↓
Executable
 ↓
LazOS
```

and says, in as many words, not to create separate executable ecosystems
unnecessarily.

## They already do

That is the honest headline. There is no roadmap item here that had to be built,
because step 61 built the C compiler's seam on purpose: the native backend takes
a `lazalith_ir::Module` and a frame layout, not a Lazen `Lowered`, and the
name-to-syscall table lives in `lazalith_os_abi` where both front ends can see
it. Step 81 recorded that as two things that had to move, and this step is the
check that they were enough.

So what step 83 does is *hold the convergence in place*. The claim is the kind
that decays quietly: a second object format for one language, a linker special
case, a fourth entry sequence, a boot path that skips the linker. Each would be
small, each would look like an improvement at the time, and together they would
be a second ecosystem.

`crates/lazalith-c-compiler/tests/convergence.rs` is the check. Four tests:

- **All three produce Lazalith objects.** The magic and the section table are
  read from the bytes, so a second object format fails at the earliest point it
  could be caught rather than at some later symptom.
- **All three run the same program to the same answer.** One program, written
  three ways, through one linker, into one image, on the real machine, compared
  against each other. A test that only *ran* them would pass with one of them
  wrong; comparing is what makes it a statement about convergence rather than
  about three programs.
- **Three objects link into one image.** Convergence is not sameness. The three
  programs are three objects with three different entry names, and the linker
  merges them into one image with one code section — which is the shape a loader
  can boot, and the reason a C object and a Lazen object can end up in the *same*
  program.
- **One entry sequence serves three entry names.** The sequence is generated by
  one function and the only thing that varies is the name it calls, so the three
  code sections are byte-identical. The difference is a relocation, not a byte of
  code. If a language ever grew its own boot path, this is what would notice.

### The program is deliberately dull

It returns 42 and writes nothing, and no library is involved. A C program that
printed something would need the C runtime linked in and a Lazen one the standard
library, and a failure would then be a failure of one of those rather than of the
route. The interesting reasons all live elsewhere — `docs/c-runtime.md` for the C
library, the SDK suites for Lazen's — and the shortest possible program is the
one that isolates the claim.

## What the three share, and what they may not

Shared, without exception, after the object exists:

| | |
|---|---|
| Object format | `lazalith_toolchain::ObjectFile`, magic `LZOBJ01\0` |
| Linker | `lazalith_toolchain::link_objects` |
| Executable | `LzxImage`, three sections: code, data, bss |
| Boot | `BootImage` and the supervisor kernel's `RFE` |
| Machine | `lazalith_machine::Machine` |
| Kernel | `LazalithKernel`, and the same `SyscallDispatcher` |
| Syscalls | `lazalith_os_abi`'s name table and record layouts |
| Entry sequence | `lazalith_runtime::startup_object_for` |
| Debug information | `.lzo`/`.lzx` source maps, read by `lazalith_debug` |

The one thing the three are allowed to differ in is the *name* of their `main`,
and only because the IR has a single flat symbol namespace:

| Front end | Entry symbol |
|---|---|
| Assembly | whatever the program calls it — `program_main` here |
| C | `fn.c.main` |
| Lazen | `fn.main` |

`fn.` is the backend's prefix for everything it emits, so a C function called
`write` cannot be the ABI's `write`. The `c.` is the module name the C compiler
chose, and it is the same reason: a C function and a Lazen function of the same
name must not collide in one program. Those two prefixes are the whole of the
per-language difference in the object, and they are namespace hygiene rather than
a dialect.

## What a second ecosystem would look like

Not as a plan — as the list of things that would break the convergence, so that
a change that does one of them is recognisable:

- A `.lzc` file next to `.lzo`, for "C objects", because the C compiler's
  relocations did not fit. The answer is a relocation kind the format can
  already represent, or a refusal.
- A linker that takes a C module and an assembly module and produces something
  the C path alone can consume. The answer is that `link_objects` takes objects.
- A `main` wrapper for C that skips the entry sequence, so a C program's startup
  differs. The answer is `startup_object_for`, which takes a name and nothing
  else.
- Booting a C image through a different path so that C can have a header C
  wanted. The answer is that an LZX image is an LZX image.
- A `printf` that is a compiler intrinsic, so C output does not go through
  `write`. It does not: `docs/c-runtime.md` has the reasoning, and it is the
  third instance of the same rule — a facility belongs to the ABI or to a
  library, not to a front end.

## The gaps this step found

None in the convergence. What it found was in the *premises*: the Lazen entry
name is `fn.main` rather than anything Lazen-specific, and the C and Lazen
startup sequences are the same instructions, which is what the last test says.
Both were already true, and the tests say so now.
