# LZ64 — ISA v1 Design Draft

## Status

Step 8 specification only. [The shared ISA](isa.md) is authoritative for encoding,
operations, flags, traps, privilege, and the Steps 9–10 API contract. LZ64 and
[LZ32](lz32.md) share one architectural model. No LZ64 CPU, instruction metadata,
memory implementation, or OS ABI is introduced here.

## Configuration

| Property | LZ64 value |
| --- | --- |
| WordWidth | W64 |
| General registers | 16 writable ordinary r0–r15, 64 bits each |
| PC / SP | Separate 64-bit registers |
| Status | Separate 64-bit value; NZCV/IE/U in bits 0..5, bits 63:6 zero |
| Pointer / virtual / physical / instruction address width | 64 bits |
| Address range | 0x0000000000000000 through 0xffffffffffffffff |
| Word bytes / stack alignment | 8 / 8 bytes |
| Instruction length / alignment | 8 / 4 bytes |
| Data sizes / natural alignments | 1, 2, 4, 8 bytes |
| Endianness | Little endian for data and instruction encodings |
| FeatureSet raw bits | Exactly 0x00000001 (BaseInteger) |

All 64 address bits are significant; there is no smaller canonical-address
subset, tagging, or implied RAM allocation. Four-byte instruction alignment is
intentional even though words and stack slots are eight bytes. MEM size selector
3 enables an eight-byte data access as part of BaseInteger, not an optional
extension; selectors 4..15 are illegal. Eight-byte LDS and LDZ have identical
full-word bit patterns. Four-byte LDS and LDZ can differ in their high 32 bits.

## Execution and width examples

- LI uses the same signed 32-bit immediate as LZ32. LI -1 yields
  `0xffffffffffffffff`; it is not a 64-bit literal instruction. Use memory or
  LI/shift/logical sequences to construct arbitrary full-width constants.
- Four-byte LDS of `0x80000000` yields `0xffffffff80000000`; LDZ yields
  `0x0000000080000000`. A one-byte LDS of `0x80` yields `0xffffffffffffff80`.
- ADD `0xffffffffffffffff, 1` wraps to zero with Z=C=1 and N=V=0. SUB `0, 1`
  yields `0xffffffffffffffff` with N=C=1 and Z=V=0. C means borrow for SUB/CMP.
- Signed range is -9,223,372,036,854,775,808 through 9,223,372,036,854,775,807.
  DIVS and REMS both trap on MIN/-1; all division/remainder variants trap on zero
  divisor. No destination or flag effects occur before trap entry.
- Shift amounts are modulo 64: 64 acts as zero, 65 as one. SAR repeats bit 63;
  SHR fills with zero. All shifts recompute N/Z and clear C/V even for zero
  effective shift. Never evaluate a host shift by 64 while building masks.
- Address `0x8000000000000000` is a valid positive address, not a negative i64.
  Applying displacement -4 produces `0x7ffffffffffffffc`; applying -1 to zero
  faults. A signed i128 intermediate or equivalent checked decomposition is
  sufficient for the full unsigned address range and signed displacements.
- An aligned eight-byte data access at `0xfffffffffffffff8` fits through
  `0xffffffffffffffff`, but an instruction fetched at that same PC cannot
  execute: checked nextPC=PC+8 overflows. PC increments never wrap, even for
  unconditional control transfers or HALT.
- PC-relative BR/CALL use checked nextPC plus signed_i32(I)*4, not a 64-bit
  immediate and not scaling by the eight-byte word/instruction size. Reach is
  -8,589,934,592 through +8,589,934,588 bytes from nextPC in both modes.

Truncation to W64 preserves all bits in a u64 container; a width mask is
`u64::MAX`. Effective address formation still checks underflow/overflow and the
entire access range. Host-u64 wrapping is not an acceptable address helper.
Address-domain wrappers remain distinct despite sharing the same bit width.

## Stack and provisional procedure ABI

SP is eight-byte aligned and the stack grows down. CALL/CALLR validate the target
and stack access, then push the eight-byte little-endian nextPC at oldSP-8,
committing memory, SP, and PC together. RET reads the full eight-byte target
at SP and commits PC and SP+8 together. Stack accesses require RAM. A faulting
push/pop or unaligned loaded target leaves the complete pre-instruction state
unchanged before the separate trap transition.

The shared provisional convention uses r0–r3 for four word-sized arguments,
r0 for a one-word return, r0–r7 and NZCV caller-saved, and r8–r15 callee-saved.
At callee entry `[SP]` contains the eight-byte return PC, `[SP+8]` argument 5,
and `[SP+16]` argument 6. Caller reclaims additional argument slots; callee
restores its entry SP before RET. Eight-byte alignment suffices at every call;
no stronger hidden 16-byte alignment, red zone, or shadow area is imposed.

Pointers and return addresses are eight bytes. Narrow unsigned arguments/results
are zero-extended to 64 bits; signed ones are sign-extended from their declared
width (in particular from 32, not always from 64). A 64-bit integer fits one
register/slot here, unlike LZ32. Aggregate/variadic/multiword rules, C `long`
size, structure layout, and the full OS syscall ABI remain future design work.

## Privilege and LZ32 interoperability

Supervisor/User permissions, status low-bit positions, trap causes, and interrupt
delivery rules are the shared ISA rules. Wider trap resume PC/SP/status values
do not imply a guest-memory trap-frame format. The controller snapshots exact
pre-entry state before privilege/PC mutation. Entry does not push or switch SP;
handlers establish their own safe Supervisor stack. RFE restores validated
resume PC/SP/status, leaving general-register results as the handler arranged.

LZ32 has the same encoding, instruction alignment, register names/count, signed
immediates, branch scaling, and BaseInteger feature bits. Width-sensitive
arithmetic, pointers, stack slots, and memory sizes differ. Shared bytes do not
imply binary compatibility; no instruction changes mode or automatically
converts pointers. A future LZ64-to-LZ32 address conversion must reject values
above `0xffffffff`, not discard their high bits.

## Step 9–10 acceptance inputs

ArchitectureConfig must report W64, 64-bit words/pointers/addresses, 16 registers,
eight-byte instructions aligned to four, eight-byte stack alignment, and exactly
[1, 2, 4, 8] supported data sizes. FeatureSet accepts only BaseInteger bit 0 alone.
Step 10 tests should cover the u64::MAX mask, source-width sign extension,
64-bit carry/borrow/signed overflow, modulo-64 shifts including zero, MIN/-1 and
zero-divisor traps, checked high-half address arithmetic, and inclusive access-end
versus nextPC boundaries. These are future test obligations, not implemented
ISA behavior or passing ISA tests in Step 8.
